# 水枢公共基础设施与插件化宪法增补条款

编号：SHUISHU-CONSTITUTION-ADDENDUM-001  
版本：v1.0  
日期：2026-09-06  
适用对象：水枢 / Cogiens Workforce OS、执行网关、插件及接入水枢的业务产品。  
依据：Doctor 本次明确指令——水枢是公共基础设施，禁止重建 APP／CP，全部功能插件化，并标准化接入外部插件。  
状态：核心原则已经用户确认；本文件为执行条款，待并入已核定的 Cogiens 总宪法主文件。未声称已修改远程仓库或完成任何插件接入。

## 第一条：公共基础设施定位

水枢是 Cogiens 生产流水线共用的任务编排、能力连接、执行调度与结果追溯基础设施。各产品通过水枢调用公共能力；产品需求不得驱动另建彼此隔离的调度系统、身份体系和管理后台。

本条中的“公共”指各授权产品共同复用，不代表无需鉴权或直接向互联网公开。

## 第二条：现有 APP 与 CP 的唯一性

客户继续使用现有 APP，平台管理员继续使用现有 CP。水枢通过它们已有的插件挂载机制、API 或 SDK 接入。禁止借接入之名重写、复制或另建 APP／CP、客户账户、角色与权限体系。

现有功能尚未形成接口时，应在原公共模块中补充接口及版本说明。水枢仅实现必要的适配与连接。不得以源码暂未找到、接口暂未核实为理由新建替代系统。

## 第三条：功能插件化与最小内核

所有业务功能、工具能力、模型后端、开发执行器、数据连接器、渠道连接器以及 APP／CP 展示扩展，都必须具有明确的插件边界与版本化契约，支持发现、配置、启用、停用、升级和替换。

内核仅保留插件注册与加载、契约校验、调度、权限执行、事件及产物路由等维持平台一致性必需的机制。身份、文件、通知、计量等已有公共设施通过适配器调用；插件不可关闭内核的鉴权、隔离和审计约束。

插件化不要求每个函数单独部署，也不要求所有插件都成为远程服务。应按独立业务能力划分，避免增加无意义的网络调用。

## 第四条：复用先于新建

每个工单进入实施前，必须记录现有能力查找结果、权威源码位置、维护责任人、接口版本、复用方式及最小缺口。

已完成且可复用的功能应登记为公共能力。重复复制实现、建立第二份权威数据或绕开公共服务的方案不得作为常规接入方案。成熟但未封装的功能，应优先在原模块完成封装。

## 第五条：外部标准接入

水枢必须提供外部协议适配层，使外部插件能够保留其原生标准，通过适配器映射到水枢内部契约。优先复用成熟官方 SDK 和原生接口，不要求外部生态全部改写成水枢专有实现。

首批评估范围包括工具协议类（如 MCP）、HTTP API 描述类（如 OpenAPI）、事件与回调接口，以及开发执行器原生 CLI／SDK。上述为接入范围要求，不代表当前已经实现兼容，也不将不同类别视为可互换协议。

每个接入必须固定实际支持的标准名称、协议版本、传输方式、认证方式、能力子集与限制。未经验证的能力登记为“未验证”；部分兼容登记为“部分兼容”，不得笼统宣称“兼容全部插件”。标准版本与实现细节在实施时核对其官方规范并留存来源。

## 第六条：插件登记契约

每个插件至少登记以下信息。字段名称为本增补建议的契约字段；落地时先映射现有注册表，禁止重复建设注册中心。

| 信息 | 最低内容 |
| --- | --- |
| 身份 | plugin_id、名称、版本、责任人、来源、许可证、包摘要 |
| 兼容性 | 原生协议及版本、适配器版本、宿主支持范围、依赖 |
| 能力 | 明确动作、输入输出结构、只读或写入副作用、文件/代码执行能力 |
| 权限 | 所需权限、凭据引用、租户及项目作用域、网络和文件访问边界 |
| 执行 | 同步/异步、超时、取消支持、重试条件、幂等要求、资源上限 |
| 交付 | 输出类型、产物元数据、校验方式、任务和事件关联 |
| 运维 | 健康检查含义、安装/升级/禁用/卸载、迁移和回滚路径 |
| 证据 | 测试时间、环境、通过项目、未通过项目、已知限制 |

SDK 是调用便利层，不能替代契约校验；插件和 API 也不能互相冒充。

## 第七条：统一权限与客户隔离

租户、用户、角色和项目权限来自现有身份及权限设施。水枢必须在服务端验证，不得相信客户端随意传入的 tenant_id，也不得仅靠隐藏菜单实现隔离。

插件仅取得任务所需的授权范围；外部插件不得扩大调用者权限。客户只能访问被授权的任务、日志和产物。停用或撤销授权后，新调用必须停止获得相应权限。

## 第八条：任务与交付契约

插件调用必须关联任务、项目、租户、执行实例、插件版本及实际后端。记录进度、原始错误、取消结果、资源用量和产物位置。对不支持的取消、流式输出或用量统计须明确声明，不得伪造。

产物必须区分文字回复、源码变更、构建包、测试报告和其他文件，并通过现有文件设施提供授权访问。敏感凭据不得进入任务正文、输出和审计日志；任务内容的留存沿用公共数据策略。

文字生成插件不得标记为已具备代码开发能力。软件开发完成必须有实际变更、执行或测试证据、可取得的产物及明确验收结论。

## 第九条：真实状态

已注册、已安装、可连接、推理通过、工具调用通过、任务完成和业务验收是不同状态，必须分别记录。

禁止用一个模型已安装证明所有执行单元可用，禁止用一次测试标记长期稳定，禁止用 HTTP 200、进程启动或“已完成”标签代替真实交付验收。

## 第十条：部署与生命周期

香港侧优先承载已有 APP／CP 的水枢入口及必要服务，M-3 承载适宜本机的模型和开发执行能力。远程连接必须保留统一身份、任务关联、超时与错误传递。具体拓扑以真实服务器和既有设施核验结果决定。

安装、配置、升级与回滚应由现有管理设施承载，普通客户无需操作 SSH、PowerShell、端口或配置文件。依赖失败必须给出可理解的状态和后台诊断信息。

升级前核验兼容性并保存回滚依据；卸载不得删除其他插件或客户共有数据。插件故障应限制在其权限和执行边界内。

## 第十一条：验收与主线门槛

以下证据齐备后，接入才可标记为通过：

1. 从现有 APP 下达任务，取得真实结果；客户无须第二次注册。
2. 在现有 CP 管理插件和权限；未建立替代后台。
3. 不同租户不能读取、取消或下载彼此未授权任务及产物。
4. 至少覆盖正常执行、失败、超时、权限拒绝，以及插件所声明支持的取消场景。
5. 外部标准完成版本对应的能力测试，并标明不支持的功能。
6. 产物可查看、下载并追溯到执行插件及版本；软件成果另有代码与测试验收。
7. 升级和回滚保留已有任务记录与客户数据。

缺少证据的项目标记“待验证”。上述要求须转化为可复用契约测试；测试能自动检查的部分纳入现有 CI，架构复用和业务结果由评审核验。

## 第十二条：实施顺序与责任

第一步，维护工程师定位现有 APP／CP、公共身份、插件注册、文件服务和接口文档，提交真实位置及版本。

第二步，Harness 根据事实建立复用映射与最小连接补丁；不自行假设接口、地址或凭据。维护人核对公共模块变更，审查者核对隔离与兼容性证据。

第三步，以一个真实业务插件贯通现有 APP→水枢→执行器→产物→现有 APP／CP，再扩展插件范围。Doctor 负责业务验收与核心架构变更决定，不承担日常命令中转。

本增补并入主宪法后，各仓库开发入口、工单模板和发布检查引用同一编号与版本，避免散落副本各自修改。核心原则变更由 Doctor 明确决定；普通兼容性修复按既有工程流程执行，不逐项追加用户审批。

## 第十三条：大模型与 Harness 选择权（2026-09-08 补充）

“大模型与 Harness”为水枢必须提供的一级能力入口，平台运营者与多租户客户均应获得授权范围内的选择能力。客户入口由现存 APP 承载，管理与授权由现存 CP 承载。

模型、Harness、执行节点必须独立标识，再形成经服务端核验的执行组合。模型已下载、适配器已配置、连接检查通过、推理验收通过、工具任务验收通过与业务验收通过分别记录，不得混用。

本地资源不足时，应允许用户选择已接入的云端先进模型。可用目录须来自真实配置与能力证据，不预设某一厂商永久最先进，不用模型名称暗示已具备文件操作、开发或工具执行能力。

付费执行遵循现有授权、计量、配额及费用结算设施。已授权的预算范围内不要求重复确认；未建立有效授权或费用控制时不得自动升级付费模型。个人会员资格不得被系统自动解释为向所有租户提供服务的授权。

租户身份由现有可信身份设施解析。模型目录过滤、派单、工作目录、任务读取、取消及产物下载均须执行服务端权限验证。身份、隔离或计费未验收的功能必须标记待接入，不能因展示了栏目就宣布多租户功能完成。
